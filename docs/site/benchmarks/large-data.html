Large-data and milestone measurements

Measured on one machine: Windows 11 Pro, 20 logical cores, release builds (cargo build --release). Times are wall-clock and come from a single run each. Peak memory is the peak working set of the tptdyn process, sampled while it runs. These are not comparisons against PyROOT or GROMACS: neither is installed here.

tptdyn analyze on a 10 GB CSV of collision events (todo Phase 1)

Input generated with the existing generator, 27.3 million events:

cargo run --release -p tpt-dynamics-data --example generate_events -- --events 27300000 --seed 42 --out data/events-10gb.csv

File size 10.49 GB, 193,865,203 particle rows (8 columns).

tptdyn analyze data/events-10gb.csv --filter "pt > 5" --hist pt,100,0,100 --hist eta,100,-5,5 --out-dir data/analysis-10gb
QuantityValue
Rows read / kept by pt > 5193,865,203 / 16,894,431
Wall time293.5 s (about 36 MB/s, single-threaded parse)
Peak working set554 MB

The streaming loader was verified against an independent Python calculation on a 300k-event file (one chunk) and a 200k-event file (two chunks). Row count, min, max, mean and population standard deviation agreed to all printed digits, and the histogram entry count matched.

Before this change analyze read the whole file into memory, so the peak would have been the size of the table, not the chunk size.

tptdyn analyze --trajectory on a 2.9 GB trajectory (todo Phase 6)

Input generated by the new generate_trajectory example:

cargo run --release -p tpt-dynamics-data --example generate_trajectory -- --atoms 100000 --frames 3200 --precision f32 --out data/traj-3gb.trj
QuantityValue
File size2,917,910,253 bytes (3200 frames, 100,000 atoms, f32)
Wall time33.6 s
Peak working set97 MB

Peak memory does not grow with the file: the reader holds one decoded chunk at a time. The CI test tpt-dynamics-data/tests/trajectory_memory.rs checks that bound on a smaller trajectory.

Distributed lazy plans (todo Phase 7)

The coordinator and workers are tested over loopback TCP (see tpt-dynamics-data/tests/distributed.rs). Those tests check that the result equals a local run. They do not measure throughput, and they have not been run across separate machines.

Not measured here

  • 1M-atom strong and weak scaling beyond 20 threads: this machine has 20 cores. The existing data is in scaling-raw.txt.
  • Comparison with PyROOT / RDataFrame and GROMACS: neither is installed.

Parallel CSV parsing (later the same day)

tptdyn analyze now parses fields on the rayon pool (CsvReader::next_batch) and converts columns in parallel. The same 10.49 GB file, same arguments:

QuantityBeforeAfter
Wall time293.5 s215.7 s
Peak working set554 MB552 MB
Histogram outputbyte-identical

The remaining serial work is line reading, the per-field String allocations, and the running statistics and histogram folding, which run on one thread per chunk. Those are the next candidates if the PyROOT comparison needs more speed.
